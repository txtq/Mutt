# Pictures

Part of the map of how Mutt is built (`CLAUDE.md`, Architecture, lists every file). Keep it current when this feature changes.

- Where a photo or video was taken never leaves in the file: `mutt/privacy.py` blanks it in place (EXIF GPS, XMP place fields, IPTC place names, QuickTime/MP4 location; same size, nothing decoded) right after `media.read` has kept it in `meta.media` for the owner, at upload, for a picture saved from a link and for a picture put in a document. `privacy.start_sweep()` (started by `server.py`) does files stored before, marking each `meta.unplaced` (`doc_images.unplaced`). Anything new that stores someone's picture or video calls `privacy.forget_place` / `forget_place_bytes` first.
- Photo editor (`photoedit.js` + `photo.css`, fetched by `editPicture` in `actions.js` the first time; a room over the file view, `DESIGN.md` "Photo editor"): crop, turn, mirror, straighten, light, colour, black and white, sharpen, soften, vignette, drawing and words, and a size to save at. The shape is drawn on a 2D canvas, the look in one WebGL pass (`Finisher`), the marks on top, all in the browser. Saving sends the finished picture to `POST /api/blocks/<id>/picture?w&h` (it takes the file's place everywhere; the first time, the file's original is kept in `meta.original`) and the settings to `PUT .../edit` (`meta.edit`, so reopening carries on from the original). `GET .../original` serves the original to its owner; `POST .../original` puts it back. An edited file's address carries `?e=` so caches let go. `public_meta` hides `original`'s keys and `edit` from everyone else. Which pictures: `canEditPicture` in `kinds.js` and `EDITABLE` in `api.py` (not GIF or SVG). It opens on the picture's preview while the whole one downloads (`standIn`, `waiting`, `arrived`), and the screen keeps its shape and the WebGL copy between paints (`screen`, `forget`), so a slider or a pen line only redoes the light or the marks.
- Media previews (thumbnails, posters, PDF first pages) are made in the browser during upload; the server never decodes media. It reads file headers only (`mutt/media.py`: camera, when and where, song tags, document kind) into `meta.media` / `meta.doctype`.
- What a picture shows is read on the device: `see.js` runs CLIP ViT-B/32 (picture half, q4) in `see-worker.js` with onnxruntime-web from cdnjs, and saves 512 int8 numbers as `meta.see` (`PATCH /api/blocks/<id>` with `see`). `mutt/sight.py` scores them against `mutt/sights.json` (kinds of picture and subjects; changing it re-labels on next read) and serves the model at `/api/see/model` (downloaded once into `DATA_DIR/models`, sha-checked; `MUTT_SEE=0` turns it off, `MUTT_SEE_MODEL` points at a local copy; tests run with it off). Autosort uploads of pictures/videos upload first, read, then call `POST /api/blocks/<id>/autosort`. `public_meta` hides `see` from everyone and place, time and camera from non-owners. Search uses the same reading: when every typed word means a subject or kind of picture (`PICTURE_WORDS` in `lexicon.py`, read by `sight.asked`), pictures that show it (`sight.shows`) come back beside the word matches; word search never looks inside `see` itself.
